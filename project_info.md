## 2. The problem

**Anti-money-laundering (AML) transaction monitoring.**

Real-world framing: bank transaction-monitoring systems produce huge volumes of false-positive alerts that analysts must manually clear, while genuine laundering often slips through. The reason is structural:

> A single transaction rarely looks illicit. A *subgraph* of transactions often does.

Laundering shows up as patterns **across accounts** — fan-out, fan-in, cycles / round-tripping, gather-scatter, stacking — not as anomalous individual rows. This is the core thesis of the project and the reason for the technical approach below.

Consequently, a plain tabular classifier (amount, currency, timestamp → label) caps out fast. **Graph-derived features are the differentiator.**

## 4. Technical approach

### 4.1 Build the transaction graph
Accounts = nodes. Transactions = directed, timestamped, weighted edges (weight = amount; attributes for currency and payment format). `networkx` is acceptable at HI-Small scale. Down-sample by time window if graph computation becomes slow.

### 4.2 Engineer graph features (the core contribution)
Compute per-account, then attach to each transaction for **both** sender and receiver:

- **Degree/volume**: in-degree, out-degree, in-volume, out-volume, and the **in/out volume ratio** (pass-through accounts are a layering signature).
- **Timing**: elapsed time between an account receiving funds and sending them onward. Fast turnover is far more suspicious than money that sits.
- **Centrality**: PageRank and degree centrality. Approximate betweenness only if time permits — **exact betweenness is too slow, do not attempt it.**
- **Community structure**: Louvain community detection; use community size and density as features. Laundering rings form small dense subgraphs.
- **Cycle involvement**: bounded-depth (2–4 hop) directed path search within a time window to catch round-tripping. Do **not** implement general cycle enumeration.
- **Ego-network stats**: mean degree/volume of an account's immediate neighbours.

### 4.3 Handle temporal leakage properly — this is a differentiator, do not skip it

Naively computing graph features over the entire transaction history leaks future information into features for past transactions. Our approach:

- **Snapshot graphs.** Discretize time into fixed windows (daily or weekly depending on density). At the end of each window, build the graph from transactions **up to that point only**, and compute the expensive features (PageRank, centrality, community) once on that snapshot. Transactions in window *N+1* use features from window *N*'s snapshot. Causally correct and computationally tractable.
- **Rolling lookback.** Consider restricting each snapshot to a trailing window (e.g. 30 days) rather than all prior history. This is not just a leakage fix — recency also matches how laundering rings actually behave (recent bursts, not lifetime patterns).
- **Cheap features may use running counters** (degree, volume, timing) updated incrementally in timestamp order — naturally causal, O(1) per transaction.
- **Temporal train/test split, never random.** Train on the earlier portion of the time range, evaluate on the later. Random splitting leaks ring structure across the split even with correct features.

If time pressure forces a shortcut, the acceptable fallback is: compute cheap features causally, compute expensive structural features on the full graph, and **explicitly flag in the report exactly which features have look-ahead leakage and why**. Be precise about the shortcut rather than blanket-disclaiming everything.

### 4.4 Models
Progression — each step must be justified by measured improvement, not assumed:

1. **Baseline**: logistic regression or a single decision tree.
2. **Bagging**: Random Forest / Extra Trees — shows variance reduction.
3. **Boosting**: LightGBM or CatBoost — expected to be the strongest single model on tabular data. CatBoost if we want native categorical handling.
4. **Stacking / blending**: 2–3 *structurally diverse* base models, out-of-fold predictions, simple meta-learner (logistic regression). Use `sklearn`'s `StackingClassifier` so out-of-fold generation is handled correctly — **in-sample stacking leaks and is a bug, not a shortcut.**

**Do NOT build a Graph Neural Network.** Hand-engineered graph features into a gradient-boosted ensemble gets most of the value at a fraction of the implementation risk. GNNs (GraphSAGE etc.) go in the report's "future work" section only.

**Cap the stack at 3–4 base models.** Beyond that, training time balloons, gains shrink, and explainability suffers — which costs us more with judges than a marginal metric gain wins.

### 4.5 The headline experiment (ablation)
Train the identical ensemble twice:
- **A**: tabular features only
- **B**: tabular + graph features

Report the lift. **This ablation is the headline result** — it proves the thesis rather than asserting it.

### 4.6 Simulating the production loop on static data
To demonstrate understanding of how this behaves over time without building any live system: **walk-forward / rolling-origin evaluation.**

Split into ~6 sequential time blocks. Train on block 1 → predict block 2 → add block 2's labels → retrain → predict block 3 → repeat. Plot performance per block.

Also run the **no-retraining control**: train once on block 1, predict blocks 2–6. Charting retrained vs. never-retrained performance is a strong, uncommon report exhibit.

## 5. Evaluation

- **Do not use accuracy.** Severe imbalance makes it meaningless.
- Primary: **precision-recall curve and AUPRC**. ROC-AUC is misleading here.
- **Per-typology recall breakdown** using `HI-Small_Patterns.txt`. Expect graph features to help disproportionately on structurally-patterned typologies (cycles, fan-out/fan-in) versus isolated anomalies — that asymmetry is a genuine, defensible finding, not a failure.
- **Business-framed metric**: "alerts generated per day at 90% recall." This is how a real compliance team judges a model and is far more compelling than "F1 = 0.87."
- **Error analysis**: where does the model fail, and why. Name the weaknesses.
- **SHAP** on the final tree ensemble — do graph-derived or raw transaction features dominate?

## 6. How this would work in production (report section only — DO NOT BUILD)

Include this as a systems-thinking section in the report. It is documentation, not an implementation target.

**Scoring path (fast, continuous):**
`Transaction stream (core banking) → Feature pipeline (graph snapshot features) → Scoring service (ensemble + SHAP) → Alert queue (ranked by risk) → Analyst dashboard (investigate + disposition)`

**Retraining loop (slow, human-gated):**
`Analyst dispositions → Labelled data store → Training pipeline (scheduled or drift-triggered) → Model registry (manual approval gate) → Scoring service`

Key points to make in the report:
- The model **prioritizes human attention**; it never makes the final call.
- The two loops run at **completely different speeds** — the model does not learn from its own predictions, it learns from analysts' verdicts on those predictions.
- **Label lag is severe** in AML (weeks to months) — a newly scored transaction has a prediction, not a label.
- Training is automated; **promotion to production is a human decision** (model validation, documented comparison, regulatory sign-off).
- Models are retrained **from scratch** on accumulated data rather than updated incrementally — auditability matters more than freshness when a regulator asks you to explain an eight-month-old decision.
